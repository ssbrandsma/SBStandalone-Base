# Standalone Base inbound TLS architecture

## Implementation

`portal.c` integrates a second listener into the existing Mongoose 7.17 event loop; handlers, assets, pairing, Virtual Radio and VPN IPC are shared. HTTP normally remains on 80 and HTTPS defaults to 443. `--https-port PORT` (or the trusted launcher environment `SBWEBSERVER_HTTPS_PORT`) selects an alternative; zero disables HTTPS. Test/nonstandard HTTP ports do not implicitly bind 443. Binding or identity failure leaves HTTP intact, with sensitive LAN writes disabled.

Host builds use Mongoose's OpenSSL backend for native tests. ARM uses its wolfSSL backend and a dedicated static wolfSSL 5.9.4 portal prefix, built by `scripts/build-portal-tls.sh`. The outbound proxy's hardware-tested library/options are preserved. The portal enables certificate/key generation and the OpenSSL compatibility APIs required by Mongoose. Small vendor-backend compatibility changes expose wolfSSL PEM readers and preload the server certificate/key into its context before SSL_new (required by wolfSSL); ARM generation uses wolfSSL native Cert/wolfCrypt APIs because the OpenSSL-compatible extension constructor is a stub. The application adds no TLS protocol implementation. Host/OpenSSL testing is distinct from ARM/wolfSSL acceptance.

The initial identity is ECDSA P-256 with SHA-256, a random 128-bit serial, CA:false, digitalSignature/serverAuth, SANs for the existing local name and current IPv4 addresses, and a five-year validity interval. ARM certificate generation uses native wolfCrypt rather than a stubbed OpenSSL-compatible extension constructor. Generation requires a plausible clock and 128 credited entropy bits (matching P-256 security strength) before seeding the kernel CSPRNG used by the TLS library; it fails closed on entropy shortage. On original kernels this uses nonblocking `/dev/random`, then mixes those bytes into `/dev/urandom` using the kernel write interface; no entropy count is fabricated. wolfSSL RAND_seed alone does not incorporate caller-supplied bytes, so it is not relied on for this mixing. A private, owner-checked boot-ID witness under `/tmp/sb-web-entropy` avoids draining entropy repeatedly within one boot. There is no persistent entropy secret or new daemon. [Linux 2.6.26 random_write](https://raw.githubusercontent.com/torvalds/linux/v2.6.26/drivers/char/random.c) mixes both output pools. Identity is generated once and reused. Expiry/corruption/mismatch does not authorize replacement. Self-signature, matching private key and validity dates are checked before enabling HTTPS.

`<persistent configuration>/tls/` is 0700; `device.crt` and `device.key` are owner-only 0600 regular files, bounded in size and opened relative to pinned directory descriptors without following symlinks. The trusted configured root is resolved once, supporting the firmware-managed storage alias. Creation writes/fsyncs both files in a private transaction directory, then renames/fsyncs it into place. Rotation is only a trusted internal capability operation exposed by a physically guarded Jive confirmation, with an interruption marker and rollback. Ordinary browser APIs cannot rotate identity. Keys never enter package archives, public responses, logs or ordinary configuration backups. The existing process core-dump prohibition applies.

TLS 1.2 is the minimum; TLS 1.3 remains enabled. TLS 1.2 uses ECDHE-ECDSA with AES-GCM. At most 12 accepted TLS connections and two concurrent TLS handshakes are admitted. Extra admitted sockets wait without allocating TLS contexts or reading ClientHello as HTTP. Handshake/queue deadline is ten seconds; established idle deadline is sixty seconds. Buffered TLS request input is bounded at 2 MiB, while existing per-endpoint upload/streaming limits remain. Persistent HTTP connections reuse the established TLS transport; cross-connection session resumption is not promised because Mongoose creates per-connection contexts.

## Authentication boundary

Backend decisions use the actual accepted `is_tls` connection flag, never `X-Forwarded-*`. HTTPS cookies use `__Host-sb_secure`, Secure, HttpOnly, SameSite=Strict and Path=/; HTTP retains `sb_session`. Stored session records include an in-memory transport class. HTTP tokens remain HTTP-only even if renamed to the HTTPS cookie name. HTTPS sessions are memory-only (one-day maximum); legacy remembered HTTP hashes remain in their existing private store. Revocation clears both classes.

Physical PINs are scoped at issue time: legacy Show Pairing Code authorizes HTTP; Secure Web Pairing Code authorizes HTTPS. Consuming a PIN on the wrong transport is rejected. The HTTPS page disables PIN entry until the user acknowledges a full comparison with the physical certificate fingerprint. That acknowledgement is UI guidance, not a custom cryptographic protocol or proof detectable by the server. The browser certificate check authenticates the device; the PIN authorizes the browser.

Host validation accepts only local interface addresses, localhost and the existing device hostname/local alias with the actual listener port. The actual accepted destination is resolved once with getsockname; ordinary native and browser requests avoid repeated network-interface enumeration. Origin comparison includes exact HTTP/HTTPS scheme and authority. Forwarding headers do not change either decision. Existing cookie/CSRF and native loopback-capability boundaries remain. `auth_sensitive_transport()` is reusable by future sensitive endpoints: it requires the transport-appropriate paired session and either actual TLS or approved loopback recovery. VPN profile CRUD uses this check; native capability routes still cannot provision profiles. Existing OpenVPN importer, redaction, atomic storage and password semantics are unchanged.

## Building

Host development builds need OpenSSL development headers/libraries; HTTPS is enabled by default (`SB_WEB_TLS=ON`). `SB_WEB_TLS=OFF` retains a deliberately HTTP-only build with LAN provisioning blocked.

For static ARM builds, first run `sh scripts/build-portal-tls.sh`, then the existing `sh scripts/build-arm.sh all`. The portal prefix is separate from the proxy prefix; `ARM_PORTAL_TLS_PREFIX` overrides it. Exported wolfSSL options must match the library's integer capacity and server renegotiation-info/extended-master-secret configuration. The server sends secure-renegotiation information for TLS 1.2 without enabling application renegotiation. Never fix an interoperability failure by enabling obsolete TLS or relaxing browser checks.

### Portal dependency provenance

The portal build pins the official wolfSSL `v5.9.4-stable` archive, SHA-256 `82dbbbb89862c1e29cfe25259d9a1c781e9ecc5db72aeb50a535bc2b819ccbc7`. `scripts/fetch-portal-tls.py` checks the archive before extraction. The build records library provenance and preserves upstream COPYING in the candidate package. New post-quantum defaults are disabled for these legacy ARM targets. The outbound proxy keeps its separate existing library. The upgrade follows review of [upstream security advisories](https://www.wolfssl.com/docs/security-vulnerabilities/); earlier development measurements used 5.8.2 and must not be interpreted as 5.9.4 measurements.

Mongoose uses host sockets and wolfSSL, rather than its built-in TCP/IP or built-in TLS stacks. Directory listings and SSI are compiled out (`MG_ENABLE_DIRLIST=0`, `MG_ENABLE_SSI=0`). These distinctions matter when assessing [upstream advisories](https://github.com/cesanta/mongoose/security/advisories); they do not constitute a blanket audit of the vendored library.

The vendored path validator has a bounded-read backport for [GHSA-cjmx-764f-286c](https://github.com/cesanta/mongoose/security/advisories/GHSA-cjmx-764f-286c). `secure_portal_path_bounds` places short, non-terminated inputs against a protected page and checks empty and traversal inputs. This addresses the common path helper used by file serving without replacing unrelated vendor APIs.

The portal library enables the portable C single-precision P-256 path (`WOLFSSL_HAVE_SP_ECC`, `WOLFSSL_SP_SMALL`; CMake `BUILD_SP` and `BUILD_SP_C`). The same feature definitions are exported for application headers. This retains the general multiprecision fallback for other supported curves and avoids assembly that requires a newer ARM ISA. Timing-resistant math remains enabled. Hardware performance must be measured after a library/configuration change.

ARM inbound TLS advertises only the `P-256` key-exchange group, matching the device identity and the accelerated implementation. The unconstrained wolfSSL 5.9.4 group list caused approximately 1.9 to 2.0 seconds of handshake CPU on Baby in the development check; a P-256-only client reduced that to 0.28 seconds. The server restriction bounds negotiation cost without permitting obsolete protocols or reducing the selected 128-bit security strength. Host/OpenSSL emulation does not establish this backend-specific policy; ARM socket tests cover it.

### Delayed startup prerequisites

The approved Baby reboot exposed a low-entropy startup: HTTP and the VPN manager started, while HTTPS correctly preserved the identity and failed closed. The listener now retries every five seconds while unavailable, so delayed clock synchronization or sufficient entropy can enable HTTPS without another process restart. Before a legacy `/dev/random` read, `RNDGETENTCNT` must report at least 128 credited bits; failed retries therefore avoid intentionally draining short pools. A concurrent entropy consumer can still cause a short nonblocking read, which fails closed. No entropy is fabricated or credited by this application. Invalid identities remain preserved during retries. The socket suite checks recovery after valid identity material becomes available without restarting the web process.
