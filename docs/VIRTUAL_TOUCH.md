# Virtual Squeezebox Touch

The Fab4 web remote uses the live Linux framebuffer and browser pointer events. It retains the Baby RGB565 capture/rotation path. All remote endpoints retain browser pairing, CSRF/origin checks, rate limits, read-only mode and protected-screen/firmware locks.

Hardware inspected on 192.168.1.244: `/dev/fb0` DISP3 BG and `/dev/fb1` DISP3 FG report visible 480x272, virtual 480x544, 32 bpp, 1920-byte stride, red 16/8, green 8/8, blue 0/8, memory 1044480 bytes. Fab4 Auto selects fb0, follows yoffset with a consistency retry and transmits little-endian BGRX8888. Unsupported pixel layouts, horizontal offsets and memory/page bounds fail safely. RGB565 remains supported without changing Baby rotation.

The authenticated remote status includes the build platform so the browser selects a Touch image and landscape canvas. Screen pointer events are serialized, coordinate bounded to 480x272 and drag updates throttled. The Lua bridge translates them into Jive mouse down/drag/press/hold/up events using the actual screen size. Tap sends PRESS then UP, matching SqueezePlay's event sequence. Reference: [SqueezePlay event constructor](https://github.com/ralph-irving/squeezeplay/blob/master/src/squeezeplay/src/ui/jive_event.c) and [mouse dispatch](https://github.com/ralph-irving/squeezeplay/blob/master/src/squeezeplay/src/ui/jive_framework.c).

The generated product image is `native/sbwebserver/web/assets/virtual-radio/touch-front.webp` (1536x1024), compressed from the built-in imagegen output. The live 480:272 canvas sits within its blank screen, with per-platform calibration stored separately from Baby calibration. The screen and full-device fullscreen views preserve the Touch aspect ratio. There are no fictitious physical button hotspots on the Touch image; optional Home/Back/playback/volume controls sit below it.

Image generation used the built-in imagegen tool. Original prompt: “Photorealistic straight-on front-facing Logitech Squeezebox Touch (2010), glossy piano-black rounded rectangular face, centered blank black landscape touchscreen, small white Logitech logo on the lower bezel, brushed silver stand, pale gray seamless studio backdrop, subtle contact shadow; no knobs, speaker grille, cables or remote; 3:2 image with no perspective distortion.” Refinement prompt: “Preserve the body, stand, lighting and background; correct only the screen/bezel geometry toward a 480:272 touchscreen, keep the screen pure black and the Logitech logo centered below it.” The precise generated black screen opening is larger than the live viewport; calibration places an exact 480:272 viewport inside it without stretching captured pixels.

Tests cover verified 32-bit geometry, stride and memory bounds, BGRX color/alpha decoding and padding, unchanged Baby rotation, Lua restricted module behavior, tap/drag/hold/up translation, invalid coordinates, firmware locks, authenticated input queue validation and the existing remote/security suite.

## On-device result (2026-10-31)

Deployed to the supplied Fab4 with the original installation/settings archived in `.local/fab4-before-virtual-touch-20261031-190259.tar.gz`. Final binary, Lua bridge, JavaScript, CSS and WebP bytes were compared against the final ZIP and matched. Persistent config and Standalone Radio were preserved.

Authenticated physical tests confirmed live `/api/remote/frame` responses with 480x272 BGRX8888, 1920-byte stride and 522240 bytes per frame, approximately 20900 microseconds capture time on this hardware. `fb0` displays the Jive interface; `fb1` is blank on this device. A down/tap at logical (220,114) from Home opened the intended Standalone Radio menu; the before/down/after captures were inspected. The bridge heartbeat is active and queued input drains. Test browser sessions were logged out afterward. Protected endpoints still reject unpaired requests.

Firmware detail: supply **all three** mouse metadata arguments to `Event:new(type,x,y,fingerCount,fingerWidth,fingerPressure)`. In this firmware the C constructor pushes the new userdata before reading optional mouse parameters, so missing trailing parameters are interpreted as userdata and raise Lua errors. The regression stub explicitly requires numeric width and pressure, and the final bridge passes 1,1,1.

During an intermediate diagnostic restart the hardware watchdog reset the device after `/var/run/squeezeplay.pid` was temporarily absent. Its pending crash log was preserved in `.local/fab4-watchdog-during-touch-testing.log`; no diagnostics were uploaded, and no crash-reporting consent setting was changed. The pending upload file was removed after preserving it locally and the prompt dismissed using Back. Subsequent updates stop only the applet-owned native services **before** using the firmware's `/etc/init.d/squeezeplay restart`, keeping file replacement outside the PID-file gap. The device is running with the corrected bridge, without new constructor errors.

Both ARM targets and package validations passed. All 60 host tests passed (153.40 seconds); Fab4-specific remote HTTP/pixel/framebuffer tests and both Lua bridge tests passed. The final constructor regression was rerun after its fix. JavaScript and Lua syntax checks passed. Windows browser screenshot automation returned a black image and browser access was unavailable, so a browser UI screenshot could not be obtained in this session; real device framebuffer captures and authenticated API input were used for physical verification.
