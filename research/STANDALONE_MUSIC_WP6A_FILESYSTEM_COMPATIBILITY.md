# WP6a filesystem compatibility and database policy

2026-11-02. This is a read-only discovery policy, **not removable-media write qualification**. No medium was connected, mounted, remounted, formatted, repaired or written on the Touch. Installed firmware evidence is authoritative for what is present; general filesystem properties do not prove that a specific old driver, USB bridge or card preserves data after unplugging.

The captured `/proc/filesystems` lists vfat, ext2, ext3, fuse/fuseblk, cramfs, unionfs, ubifs, nfs and kernel pseudo-filesystems. MediaManager advertises FAT16/FAT32/NTFS/ext2/ext3. The installed automounter explicitly selects ntfs-3g for vol_id type ntfs and special VFAT options; otherwise it tries mount -t auto. This establishes support paths, not tested media compatibility. exFAT/ext4 support is **not established** by that capture and is not enabled by WP6a. Internal UBIFS/unionfs/cramfs are not offered as removable music storage; NFS is not automatically accepted.

The [kernel VFAT documentation](https://kernel.org/doc/html/v5.17/filesystems/vfat.html) explains the name/encoding/time conversion options; actual options above come from the captured firmware script. The [FAT driver](https://android.googlesource.com/kernel/common/+/d3601e56cf64a3f2df6f6380cccb3644274406e2/fs/fat/inode.c) sets its file-size maximum to 0xffffffff. [NTFS-3G's own manual](https://github.com/tuxera/ntfs-3g/wiki/Manual) describes option-dependent name/permission behavior. These current references explain concepts and do not certify the firmware's historical binaries. A future scanner must compare size plus mtime with filesystem precision in mind and use bounded fingerprints when needed, rather than assume second-resolution equality means unchanged content. WP1's exact UTF-8 path keys do not emulate each filesystem's case folding or aliases; the scanner must preserve canonical observed paths and avoid duplicate case/alias indexing. Raw invalid-UTF-8 filenames need an explicit WP1 policy. WP6a's relative/root paths are bounded to 1023 bytes; WP1 permits longer metadata paths, so WP2 must handle this difference explicitly rather than truncate.

## SQLite placement gate

WP1 retains DELETE journaling, FULL synchronization, checked journal selection, finite busy time, explicit wal_safe for WAL and preservation of corrupt/newer-schema databases. These settings do not make an untested device safe. SQLite documents [locking and hot-journal recovery](https://www.sqlite.org/lockingv3.html), [WAL shared-memory/sidecar requirements](https://www.sqlite.org/wal.html) and [corruption causes including broken locking/sync](https://www.sqlite.org/howtocorrupt.html). WAL is never selected from a filesystem name alone. Do not use journal_mode=OFF/MEMORY, synchronous=OFF, nolock or immutable=true to bypass removal/recovery problems.

No writable or read-only removable DB is automatically opened here. WP1's filename-based VFS can create/open sidecars through a reused mountpoint; concatenating an approved root pathname would leave a TOCTOU hole after unmount. Before enabling database-on-medium, implement a descriptor-anchored VFS/lifecycle barrier, validate the selected database and sidecars, then qualify the exact filesystem/driver/media combination. Even close/checkpoint/rollback can perform filesystem I/O; removal does not make those operations safe or nonblocking. WP6b must own the close/drain/eject barrier. A root fd alone cannot complete it.

If removable DB safety remains unverified, alternatives are an explicitly selected independently qualified external database store, or a separately bounded volatile index with clear nonpersistent behavior. Internal flash is **not** a silent fallback. No policy automatically imports/deletes `.Squeezebox`, formats a device, repairs a filesystem or deletes offline tracks. Library identity can remain associated while media is offline; absence never means an empty successful scan. These restrictions leave read-only storage roots usable by future WP2 without silently authorizing persistence or safe eject.
